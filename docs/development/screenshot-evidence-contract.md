# Screenshot evidence contract v1

This contract is shared by local discovery, GUI viewing and Claude/Codex launch
guidance. Capturing screenshots requires an explicit user request for visual
validation. Registering a destination or watching it does not authorize capture.

## Ownership and directory layout

AMF allocates an immutable scope UUID for a producing AMF feature session:

```text
<canonical-workdir>/.amf/screenshots/<feature-id>/<session-id>/<scope-id>/
  owner.json
  <image-id>.png       # also .jpg, .jpeg, .webp or .gif
  <image-id>.json      # completion manifest, published last
```

IDs are ASCII letters, digits, hyphens or underscores, at most 128 bytes.
AMF creates `.amf/screenshots/.gitignore` containing `*` when no rules exist,
so registering a destination and writing evidence leave Git status clean.
Existing namespace ignore rules are preserved. Scope cleanup leaves this shared
namespace file in place.

`scope-id` is generated by AMF. Image IDs are chosen by the producer and remain
stable when replacing that image. Each file is an immediate regular child;
subdirectories, symlinks and special files are not accepted. No absolute path,
separator, parent component, NUL or percent-encoded path is accepted in a file
field. `.amf` and all descendants used for evidence must not be symlinks.

`owner.json` is AMF-written, version 1, and contains `scope_id`, `project_id`,
`feature_id`, `session_id`, `project_name`, `feature_name`, `session_label`,
canonical `workdir`, `is_worktree` and `created_at`. Original IDs and labels are
historical attribution, independent of live records and harness conversation
IDs. Producers copy the scope ID into their completion manifests; they do not
edit ownership metadata or guess the session from the last shared instruction.

A small SQLite ownership catalog stores these scope records without cascading
foreign keys to projects, features or sessions. It registers canonical paths
and scope state (`active` or `retired`) before a producer receives guidance.
This catalog is necessary to find retained repository-root and non-git evidence
after their project/feature/session records disappear. It is not an image index:
images and completion state are rediscovered from disk. Existing active scopes
are reused for repeated launches of the same session at the same workdir.
Conflicting ownership/path records are refused, never reassigned. Deleted
scopes remain tombstoned; restarting that session allocates a fresh scope ID.

## Completion and replacement

Example producer completion manifest:

```json
{
  "version": 1,
  "scope_id": "AMF-assigned-scope-uuid",
  "image_id": "dashboard-ready",
  "file": "dashboard-ready.png",
  "sha256": "64-lowercase-hex-digits-of-the-completed-image",
  "caption": "Dashboard after the requested validation",
  "captured_at": "2026-10-07T17:00:00Z"
}
```

Capture to a temporary file within the scope directory, close it, and rename
it to the final image name. Hash the final bytes. Write the manifest to a
temporary file, close it, and atomically rename it to `<image-id>.json` last.
Do not publish a manifest before the image is complete. Check that the scope
still exists with its original `owner.json` before publication; after cleanup
never recreate an old scope directory. A new image ID creates another gallery
item; replacing the bytes under the same ID and publishing the new hash updates
that item. The stable item key is `(scope_id,image_id)`; decoded/thumbnail keys
also include the byte hash. Timestamps and file size alone are insufficient.

Valid completed evidence requires matching ownership, manifest scope and image
IDs, final filename stem, supported format, SHA-256 and bounded decoding. A
manifest hash mismatch, absent image or decode failure is recoverable incomplete
evidence, not a completed thumbnail. Unmanifested images are reported incomplete
and are never attributed by filename alone. Invalid JSON, unsupported versions
and inconsistent metadata produce per-item diagnostics and never suppress other
valid items. Correcting the file is enough to recover on reconciliation; AMF
does not repair or overwrite producer data.

## Reconciliation and lifetime

Register watches before initial reconciliation. Watch the nearest existing
owned ancestor when a scope is not present. Filesystem events, including watcher
errors/overflow, only mark roots dirty. Reconcile on startup, open/reopen, dirty
events and periodic fallback while the gallery is open. Bounded scans produce
a new projection; duplicate events do not append duplicates, missed events
converge through the fallback, and writes during scanning are retried. Process
files from a bounded byte snapshot and verify its hash, avoiding partial reads.

DB scope state is rechecked when a scan/decode result is applied, with a GUI
request generation also checking the current feature/session/PR/run selection.
Closing the viewer invalidates pending frontend results. Read workers never
write into producer directories. Thumbnails and full-image transports are
transient; there is no persistent decoded-image cache to resurrect after cleanup.

Deleting a session or non-worktree feature does not delete its evidence. The
workspace's retained-evidence entry lists catalog scopes even without original
records. Cleanup selects scope IDs, one producing scope at a time;
it never deletes unrelated files outside these exact owned directories.

Explicit cleanup retires the scope in the DB before removing files. Retirement
invalidates pending results across AMF processes and is durable across restart.
If directory removal partially fails, report it and permit retry against the
same tombstoned scope. Cleanup processes at most 20,000 entries or 30 seconds
between filesystem operations per attempt, so continuous producer writes cannot
hold a cleanup worker indefinitely. Do not silently reactivate the scope. New capture after cleanup
requires a new launch scope; the old launch instructions remain retired.

Successful worktree deletion retires all scopes at that canonical workdir and
invalidates their workers; the worktree removal itself removes evidence files.
A failed worktree deletion retains active evidence. Foreground, background and
externally observed worktree disappearance use the same successful-deletion
coordination. Repository-root and non-git scopes survive feature/project removal
and missing-root observations until explicit screenshot cleanup.

## Processing limits

| Resource | Limit / behavior |
| --- | --- |
| Image bytes | 20 MiB per image |
| Formats | PNG, JPEG, WebP and GIF; GIF/WebP animation displays the first frame; SVG and other formats report unsupported |
| Dimensions | 16,384 on either axis; 40 million total pixels |
| Decoder allocation | 160 MiB; four simultaneous image retrieval/read workers and one decoder; never decode under the GUI handle lock |
| Thumbnail | Fit within 240 × 160, encoded PNG; at most 256 KiB |
| Full image transport | Validated static image, at most 20 MiB encoded bytes; no raw SVG or external source URLs in image elements |
| Metadata | 16 KiB per local manifest/owner; caption 2,000 characters |
| Scan | At most 1,000 entries per scope, 200 completed items and 100 MiB image reads per projection; report truncation and keep navigation bounded |
| Archive | ZIP only; 100 MiB compressed, 200 MiB total extracted bytes, 1,000 entries, 20 MiB/image, 200 million decoded pixels per archive |
| Archive paths | Reject absolute paths, drive prefixes, backslashes, `..`, empty components, duplicate normalized names, symlinks/encrypted members and nested archives; inspect in memory, never extract into a worktree |
| Remote reads | 30 seconds/request, 5 redirects, bounded metadata at 1 MiB, 100 pages per collection, 200 source notices/gallery browser links; retry renews signed retrieval URLs |

Invalid or oversized entries never prevent valid neighboring evidence from
being viewed. Archive-wide path violations reject that archive. Listing does
not decode every original image at once; bounded workers generate thumbnails
and the selected full image on demand.

## Public gallery manifests

A supported gallery is an explicitly linked HTTP(S) JSON manifest named
`amf-screenshots.json`, or an explicitly labelled gallery/screenshot/visual-validation link whose response declares the vendor media type
`application/vnd.amf.screenshots+json`. Do not guess sibling paths, scrape HTML,
crawl pages or execute scripts. The v1 manifest has this shape:

```json
{
  "version": 1,
  "title": "Requested validation",
  "images": [
    { "id": "ready", "url": "./ready.png", "caption": "Ready state" }
  ]
}
```

Image IDs must be unique valid IDs; at most 200 images. Resolve relative URLs
against the manifest's final URL, with the same protocol/address/credential
rules as direct images. Image identity is `(original_manifest_url,image_id)`
and replacement uses the decoded content hash. Preserve original PR link/comment
provenance alongside the manifest and resolved image URL. Protected responses,
HTML and unsupported public-gallery forms offer browser opening at the original
link; browser cookies/credentials stay outside AMF.
